# Practice 10 — The Data Arrives Later

## Level 1 — порядок событий

Прогноз: A → C → первый кадр приложения → примерно через две секунды B → 6 students. При вызове API дополнительно сразу выводится fetchStudents #1.

Фактически в проверочном Flutter-тесте получен порядок:

```text
A -> C -> first frame -> B -> 6 students
```

`first frame` записан обработчиком addPostFrameCallback. В исходном эксперименте эта строка сама не печатается. Сообщение API fetchStudents #1 выводится синхронно при запуске запроса, до первого кадра.

Future.delayed отдаёт управление циклу событий. Вариант с sleep, оставшийся в незавершённом проекте, заменён обратно на await Future.delayed: sleep блокирует текущий isolate и задерживает отрисовку. Итоговый API не использует dart:io.

Номер запроса фиксируется до await. Поэтому при пересекающихся запросах ошибку получает именно каждый третий вызов, а не все запросы, которые прочитали изменившийся общий счётчик после ожидания.

## Level 2 — mounted и четыре состояния

Проверены загрузка, список из шести студентов, пустой ответ, ошибка третьего запроса и успешный Retry четвёртого запроса.

При отдельном эксперименте без mounted после удаления виджета получено:

```text
setState() called after dispose(): _UnsafeScreenState#dcaf1(lifecycle state: defunct, not mounted)
```

Это сообщение из временного проверочного виджета. Идентификатор State меняется при каждом запуске. В окончательном StudentsScreen проверки mounted стоят и после успешного запроса, и в обработчике ошибки. Проверено закрытие экрана до успешного и до ошибочного ответа: исключений нет.

Для проверки пустого состояния тест передаёт FakeApi(empty: true). Для обычного запуска используется FakeApi(). Тире отображается вместо отсутствующего GPA.

## Level 3 — сохранённый Future

После десяти переключений Switch счётчик API остался равен 1, список оставался на экране. Переключатель изменяет только dense у ListTile.

Новый Future создаётся в initState и при явном обновлении или Retry. Поле не final, поскольку повторный запрос заменяет его значение. FutureBuilder проверяет hasError первым, затем завершённость операции, затем пустой список. Ключ по Future сбрасывает предыдущий snapshot при повторном запросе.

Создание запроса внутри build перезапускает операцию при перестроении. В окончательном коде вызова API внутри build нет.

Retry использует блочное тело callback в setState. Сокращённое присваивание Future через стрелку возвращает Future и в debug-режиме вызывает ошибку setState() callback argument returned a Future.

## Level 4 — обратный отсчёт и отмена

Обе версии проверены до нуля. Согласно порядку операций из задания, генератор сначала ждёт секунду и затем отправляет число: первое событие 10 приходит через секунду, а 0 — примерно через 11 секунд. До первого события интерфейс показывает 10.

С отменой: после Back на значении 7 и завершения удаления маршрута новых tick 6 … tick 0 нет. Это проверено отдельно для ручной подписки B и для StreamBuilder A. При переключении A/B предыдущий дочерний виджет удаляется, его подписка отменяется; новый отсчёт начинается с 10.

Без отмены в отдельном эксперименте генератор продолжил вывод:

```text
tick 7
setState() called after dispose(): _UnsafeScreenState#ef259(lifecycle state: defunct, not mounted)
tick 6
tick 5
tick 4
tick 3
tick 2
tick 1
tick 0
```

Ошибка setState повторялась перед каждым последующим tick. В проверочном виджете ошибки перехватывались, чтобы наблюдение продолжилось до нуля. Временный неисправный виджет в проекте не оставлен.

В версии B dispose вызывает cancel перед super.dispose. В версии A подписку отменяет StreamBuilder. Возвращаемый cancel Future явно отмечен unawaited, поскольку dispose синхронный; доставка новых событий прекращается после вызова cancel.

## Level 5 — сохранение

Первое сохранение успешно, второе завершается StateError. При проверке неожидаемого сохранения ошибка была перехвачена отдельной тестовой зоной:

```text
Bad state: server rejected 6
```

Без обработчика ожидаемая строка необработанной ошибки:

```text
Unhandled Exception: Bad state: server rejected 6
```

Неправильный обработчик закрывает экран до ответа сервера: пользователь видит закрытие экрана, хотя сохранение не удалось. В итоговом коде Save ожидается, StateError показывается в SnackBar, экран закрывается только при успехе. После ожидания перед обращением к Navigator или ScaffoldMessenger проверяется context.mounted.

Проверено: два быстрых нажатия дают один вызов save; кнопка на время запроса отключена; после отказа снова доступна; закрытие экрана во время сохранения не вызывает исключения.

Экземпляр ручного API хранится на главном экране, поэтому счётчик сохранений не сбрасывается при повторном открытии StudentsScreen.
